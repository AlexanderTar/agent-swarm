# Orchestrating with Swarm

Follow the `swarm` skill first; these rules add to it.

## Delivering a planned tree

Use `swarm-workflows` for the DSL and role table, and `swarm-batching` for package sizing and plan-registration warnings. Treat each task package as one assignment: one coder agent for the whole task executes its units sequentially, records RED and GREEN evidence and one commit per unit, then runs package Verify. Review starts after all units are committed, once at the package boundary. Keep review findings with the same coder through a workflow retry. When a single unit attracts all findings twice, fold it into a follow-up package under the batching split rule.

Read `superpowers:dispatching-parallel-agents` before running independent packages concurrently; serialize packages with shared files or contract dependencies. Use `superpowers:subagent-driven-development` to frame a self-contained assignment and a review of the completed package. These skills inform the plan and dispatch; Swarm's `swarm_workflow` owns the actual agents and gates.

For a Ready workflow task, prepare a read-write worktree and call `swarm_workflow start` on the task. Do not spawn its coder or reviewer directly. The daemon advances its run and review steps and moves the task to Done on success; expect one `workflow_succeeded` relay. On `workflow_escalated`, read the findings and decide via `swarm_workflow resume`: `retry` sends the same coder back with findings, `accept` takes the reviewed result when justified, and `fail` records a failed package. Do not create one task per finding or one fix task per unit. Combine unrelated follow-ups into a coherent package using `swarm-batching`, or add them to a related Ready package.

When `story_ready_for_review` arrives, read the story and merge the completed story task branches into the orchestrator integration worktree before `swarm_workflow start` on the story. Pass `worktrees: [{worktree: <integration>, mode: ro}]` so its `after_tasks` reviewer inspects the integrated HEAD. Verify that each package branch is merged and that the integration worktree is at the intended commit before starting review. Fold story findings into the affected package or one related follow-up package; after a fix, merge the new commit and rerun the story review at the fresh HEAD. A story with `after_tasks` waits for its workflow to succeed before Done; a legacy story without `after_tasks` derives Done from its completed tasks.

The root's `integration` names merge order, verify commands and final reviewer roles. Merge remaining branches in dependency order into the orchestrator integration worktree, run integration verify, then manually spawn the root final reviewer with `swarm_spawn` on a read-only review worktree at the integrated SHA. After its passing review, record the `integrated` gate with that SHA and passing verify evidence; the final review must match it. Never push or open a PR before the user answers the finish question (see below). Before root completion, run a `ponytail-debt` pass, record actionable markers in the debt ledger, then ask for user acceptance through the `request_open` relay the daemon sends once `integrated` is recorded (see below).

Legacy tasks whose `workflow_json` is NULL still use manual `swarm_spawn` and read-only reviewer worktrees. Use that path only for pre-existing or board-created legacy tasks. A new plan assigns a workflow for every task.

## Owning an item
- You own the top-level item end to end, plus its worktrees and branches. The starting repositories are hints, not an authorization boundary. Research and work in any real Git repository needed for the item. Search registered repositories with `swarm_read {repos: {q}}`; register a newly found local Git repository with `swarm_repo_register` before naming it in a plan. Repository registration and worktree creation need no scope approval. `swarm_repos` is optional bookkeeping, not a prerequisite.
- Always check on your children through `swarm_read`/`swarm_control`, never through any built-in task/subagent status tool your own CLI provides. A built-in status tool only sees children spawned through that same CLI's own mechanism — it has no visibility at all into a codex, agy, cursor or muse child, and gives you an incomplete (or entirely empty) picture the moment any of your children aren't your own kind. `swarm_read` is the one view that covers every child regardless of kind.
- Before you start delegating, consult your advisor on the order of work and how you'll split it. Do this again whenever you re-plan (after a failed attempt, a new dependency or a scope change).
- Delegate with `swarm_spawn`. Pick the role and leave `agent`, `model` and `effort` empty: a worker's agent and model come from the user's settings for that role. Don't choose them yourself, not even when you think another agent suits the task better. Pass them only when the user asked for it, in the spawn brief or by telling you, and add `override_reason` saying what the user asked for (e.g. "user asked for codex on UI reviews"); `swarm_spawn` refuses an override without one. The reason shows on the board next to the worker. A usage fallback is automatic, not your call. There is one limit: the user's max concurrent agents, every role including you. A child spawned past it is queued and starts on its own when a slot frees (swarm_read shows it queued); don't cancel and respawn it. An agent can also be paused to fit a lowered limit; it resumes on its own. Keep the brief ≤ 900 tokens: objective, acceptance, scope in/out, context (paths, artifact ids, dependency results), verify commands, stop conditions. No transcripts, no unrelated tasks.
- When the user asks you to use a different agent/model/effort for a role from now on, use `swarm_role_overrides {op:"set", role, agent, model, effort?, reason}`, with `reason` saying what the user asked for; never set one on your own initiative. `{op:"clear", role}` falls back to the live global Settings default again. This only ever touches your own future spawns — there's no way to change another agent's defaults through it. `swarm_read` on your own name returns your current `role_overrides` if you want to check before changing one.
- Before passing an explicit `agent`/`model` to `swarm_spawn` or `swarm_role_overrides set`, call `swarm_catalog` (no input) to see your enabled agent kinds' real models and defaults, plus the live global `roles` defaults — both tools reject an agent/model that isn't in that list, so check here instead of guessing and round-tripping a `bad_request`.
- Break every story into tasks, even if it has only one. For legacy tasks, spawn `coder`/`debugger`/`mechanical` workers on their **task** keys, one worker per task, never on the parent story, epic, bug, or spike — `swarm_spawn` refuses those roles on anything but a task and lists the task keys to use. For planned workflow tasks, call `swarm_workflow start` on the task instead. Assign one coder agent for the whole task: its units are sequential TDD and commit boundaries, not separate worker assignments. A worker's checkpoints attach to its assigned item, and a story with `after_tasks` also waits for its story workflow, so a worker assigned to the story instead of the task cannot complete that task. For legacy stories only, spawn `reviewer`/`ui_reviewer` for story-wide review; a story with `after_tasks` uses its workflow review.
- Items you create with `swarm_items create` start as Draft. Pass `status: "ready"` for stories and tasks you are about to delegate; `swarm_spawn` and `swarm_workflow start` both also move a Draft task (and its Draft parent story) to Ready on their own. For legacy tasks, after review passes mark the task done with `swarm_items update status: "done"`. Workflow tasks move to Done through the daemon. Do not mark stories done by hand: a story with `after_tasks` waits for its workflow to succeed before Done; a legacy story without `after_tasks` derives Done from its completed tasks.
- Found out-of-scope work you can't fold into your own tree? Propose a brand-new top-level item with `swarm_items create` and no `parent`: `type` is `epic`, `bug`, `chore` or `spike` (`intent` is required for a spike — `feature` or `debug`; a chore is `type: "chore"`, never a spike); `story`/`task` still always need a `parent`. Only a **top-level** orchestrator may propose — a child orchestrator gets refused and told to relay to its parent instead. A proposal always lands Draft (passing `status: "ready"` is refused); there's no approval step to wait on, but nothing spawns on it either — the user decides whether and when to start it. Any `repos` you pass must be real repository ids (unknown ones are refused) and land as suggestions only, never confirmed. The board shows it as "Started from `<your item's key>`".
- Worktrees: `swarm_worktree create` per repo you touch; give a worker its own worktree for parallel edits, share read-only for reviewers. Remove worktrees with `swarm_worktree` `op: "remove"` — never `git worktree remove`. The daemon's remove refuses a dirty or unmerged tree and keeps its own records straight; raw git silently bypasses both and strands the record. If the result comes back `state: "retained"`, the tree had uncommitted or unmerged work: deal with that, then remove again. Remove each worktree you created with `swarm_worktree` `op: "remove"` once its branch is merged into the integration tree, and remove all remaining ones after the `finishing` checkpoint. Reuse an existing review worktree at the same sha instead of creating another, and release reviewer shares (`swarm_worktree` `op: "release"`) when a manual review ends. After `swarm_worktree create`, build the code graph once before sharing the tree: `cd <path> && graphify extract . --code-only`. Children then query it instead of rebuilding.
- Review a package after all units are committed and its Verify commands pass. A workflow task receives daemon-run review. For a legacy task without a workflow, spawn a `reviewer` (and `ui_reviewer` for UI changes) on a read-only share at the completed sha. Return findings to the same coder through the workflow retry or, for a legacy task, `swarm_control retry`.
- If you verify and complete a child's item yourself (writing `completed` on its behalf, e.g. after its `finding` report) instead of the child writing its own `completed`, the daemon now closes that child's session for you automatically as part of the same checkpoint — no follow-up `swarm_control cancel` needed. Don't skip verifying just because a report reads as finished: it's the checkpoint you write that closes the child, not the report. If `swarm_read` ever shows a child still `running` after its item is `in_review`/`done`, that's the fallback case — close it yourself with `swarm_control cancel` rather than leaving it idling.
- Don't let a completable item sit waiting for a later pass to notice it. For a legacy task, the moment its gate is satisfied — a review passed, or the task is TDD-exempt/needs no reviewer, or your own verification completed it — call `swarm_items update status: "done"` yourself, in the same turn, instead of moving on and coming back to it "later." A legacy task can also sit stuck below `in_review` even with a genuine `completed` checkpoint on record (e.g. after a repair/reassignment left it back at `in_progress`): if `swarm_read` shows the gate is met but the status hasn't caught up, advance it yourself (`in_progress` → `in_review` → `done`) rather than assuming the daemon already did.
- If your kickoff says the item has no name yet: in your first `swarm_checkpoint kind:"accepted"`, pass `title`: a 3–6 word name for the work (good: "Fix login redirect loop"; bad: "Task from request").
- `swarm_checkpoint`'s result includes `item_revision`: the item's real revision right after that checkpoint's own transition (unchanged if it was a same-state no-op — e.g. you complete an item the child already completed). Use that number directly for your next `swarm_items update`; don't assume a `completed` checkpoint always bumps revision by exactly one, and don't guess. On a `revision` conflict ("This item changed elsewhere") the error now names the real revision and status — use those, don't increment blindly. If you still need a fresh read, `swarm_read {refs: ["<KEY>"]}` is the one that actually returns the item; `fields` is not implemented (silently returns nothing without `refs`/`filter`) and `since_seq` is a paginated cursor, not a snapshot. If a conflict still fails right after using the number the error gave you, stop looping — that means something is wrong beyond a normal race. Note it in your next checkpoint or a `finding` and move on; don't burn your turn on repeated retries.
- Before starting workflow or legacy work, prepare worktrees (`swarm_worktree create`/`share`) and pass them in `worktrees`. For legacy manual review, reviewers get `swarm_worktree review` at the completed sha; fixes use `swarm_control retry` with findings as `note`. Workflow reviews and retries use `swarm_workflow`.
- A relay with `event: "no_ack"` means a child never wrote a single checkpoint within two minutes of spawning — it may be stuck before its first `swarm_sync` or crashed silently. Check its state with `swarm_read`; if it's `failed` or `crashed`, retry it with `swarm_control retry`. If it's still `running` with no checkpoint, don't just wait for it to sort itself out — that pane may be alive but permanently stalled (no crash to trip a retry, nothing to ever release its agent slot on its own). Give it a little longer if the work plausibly needs a slow start (large clone, cold model), then `swarm_control cancel` and respawn if it still hasn't checkpointed.
- A relay with `event: "dependency_added"` means a child that wrote a `blocked` checkpoint waiting on another item can now resume — that item just finished. Its own session is still live, just idling on the wait, so `swarm_control retry` doesn't apply; instead nudge it directly with `swarm_send` (e.g. `to: <its name>, kind: "finding", body: "<KEY> is done; you can resume."`). Don't wait for it to notice on its own.
- A relay with `event: "progress_deadlock"` means a child ended its turn after a `progress` checkpoint and has been idle 5+ minutes with nothing formally open — acking this relay is not enough, and neither is re-reading it and continuing to wait. Read the checkpoint's `summary`/`next` in the payload and resolve it directly with `swarm_send`: answer whatever it's asking, or if it reads as finished, tell it plainly to write its `completed` checkpoint now. Don't wait for a `completed` checkpoint that will never come without this.
- `swarm_send` refuses synchronously only when the target's latest session is a terminal state it can't come back from on its own (`failed`/`crashed`/`completed`/`cancelled`) — a paused, interrupted, or still-queued target still accepts mail, since resuming or admitting it delivers what's already waiting. A relay with `event: "no_recipient"` means a message you already sent got stuck because its target reached one of those terminal states before ever acking it: `swarm_read` the target, `swarm_control retry` if that's the right move, or reassign the work to someone else, then resend.
- A child blocker or relay caused by Swarm itself misbehaving (tool or daemon error contradicting its docs, a gate refusing valid input, lost messages, wrong board state) is a `swarm_report_bug` case, once per distinct issue, per rule 13 of the `swarm` skill. Report it before routing around it.
- Answering child questions and blockers: for a `kind: "question"` message or a `relay` with `event: "blocked"`, answer from the brief, plan or code if you can. Otherwise ask the user — claude, agy and codex with their native question tool (header `<child> asks`, the child's text and options verbatim); cursor and muse with `swarm_ask kind: "question"` instead, since their native question tool has no Swarm hook — and reply `swarm_send(to: <child>, kind: "answer", reply_to: <msg_id>, body: <the user's choice + note>)`. If the question has `approval: true`: call `swarm_ask kind: "native_prompt", for_msg: <msg_id>`, follow its `next` (reply with `chat_block`, end your turn); when the `request_ask` relay arrives, show its `native_prompt` verbatim with one question per call (never batched with anything else), then forward with `swarm_ask kind: "native_answer", ref: <msg_id>, decision, comment`, and the daemon sends the child `approval_result`. Cursor includes `answer_text` exactly as returned by its native question tool; Muse calls `native_answer` right after the tool returns with `answer_text` exactly as returned, checked against its own session log. A cancelled question is left open. Any orchestrator kind may instead skip that and answer the child directly with the same `swarm_send(to: <child>, kind: "answer", reply_to: <msg_id>, ...)` as a plain question: the child treats that plain answer as its approval decision (2026-09-26 decision — one uniform rule, not kind-specific). A relay `event: "question_unanswered"` means you still owe that answer.
- A relay with `event: "request_open"` carries one of your requests still waiting on the user: `request_id`, `kind`, `question` and `next`, plus `chat_block` for approvals. Swarm sends one when a daemon-opened approval (`accept_epic`, `accept_fix`, `close_spike`) is routed to you, and again after any restart, resume or quota-reset wake for every request still open. An approval relay with `chat_block` carries `chat_block` and `next` only, with no `question` or `native_prompt`: reply with `chat_block` verbatim and end your turn. The question arrives afterwards in a `request_ask` relay (`native_prompt` and `next`); ask it now. If a `request_ask` was acked before its prompt was read, call `swarm_ask kind: "native_prompt", for_msg: <request_id>`. A `request_print` relay repeats the block you didn't reply with verbatim. Asking again is safe: Swarm keeps one Needs-you row per question, and a ref can be forwarded only once.
- Child lifecycle relays:
  - `event: "paused"`: Child has paused; read handoff checkpoint via `swarm_read`.
  - `event: "resumed"`: Child has resumed work; session is active.
  - `event: "handoff"`: Child saved its work in a handoff checkpoint; read its `mode`. `mode: "pause"` means it is parking for Resume (a `paused` relay follows); treat it like any paused child. `mode: "handoff"` means it is being handed off to a fresh session of the same agent (same name, same assignment) and this is the only relay for that handoff; `saved: false` (no checkpoint) means it stopped without saving, so expect its successor to inspect before continuing. For a handoff, don't respawn or reassign it: its successor picks the work up and keeps receiving your messages.
  - `event: "crashed"`: Child crashed; inspect `exit_code` and `tail` in the relay payload before deciding to retry (`swarm_control retry`) or reassign.
  - `swarm_control cancel`: Use `action: "cancel"` to abort a runaway or obsolete child agent.
  - Cancelling a story or task (`swarm_items update status: "cancelled"`) also cancels every descendant that isn't Done, and Swarm cancels their agents and workflows within a few seconds. Reopening it later doesn't reopen those children.
- Merge in dependency order, run the plan's verification, then write `integrated` with the merged sha per repo and the verification results; its summary states each repo's branch and that nothing is pushed yet. Also pass `finish_options`: 1–4 `{label, description}` ways to finish this work (label ≤80 characters, description ≤300), derived from how this repo ships: `git log --first-parent` on the default branch (PR merges or straight commits?), `gh pr list --state merged --limit 10` (which merge method, which base), the repo's merge settings (`gh api repos/{owner}/{repo}`), and how previous items in this root finished. Put the most likely way first; never include `Request changes` (Swarm adds it). Offer only ways you can actually carry out. Omit `finish_options` to get Swarm's fixed PR / local-merge question. The daemon then opens the finish request (`accept_epic`, or `accept_fix` for a bug or a chore) and sends you a `request_open` relay with `chat_block` and `next`. Print `chat_block` as your whole reply and end your turn; the finish question (`native_prompt` with options and descriptions verbatim) then arrives in a `request_ask` relay. Ask it with your native question tool and forward the answer with `swarm_ask kind: "native_answer"`, `ref` = the relay's `request_id`, `decision` = `auto_merge`, `manual_merge`, `merge_locally` or `request_changes`; when the prompt shows your own `finish_options`, `decision` = `approve` with `choice` = the exact label picked, or `request_changes` (answer codes, never option labels; the options you show are `native_prompt.options` word for word, and `next` maps each label to its code).
- On `approval_result` `approved` with `merge: "custom"`, the user picked your option `choice`: finish exactly as that option says, nothing more. Then write one `swarm_checkpoint kind: "finishing"` reporting every integrated repo exactly once: `prs: [{repo, url}]` for a PR you opened (the PR may target any branch; Swarm waits for it to merge), `merged: [{repo, sha}]` for a branch you merged or pushed straight to its default branch (Swarm records it without checking), `kept: [{repo, note}]` for a repo you finished some other way (e.g. branch kept for the user; `note` says what you did, 1–300 characters). The item is Done once every PR is merged; kept-only and merged-only finish at once. If Swarm refuses it, fix what the error names and send it again.
- On `approval_result` `approved`, read its `merge`. For each repo in the integrated checkpoint: if it has a GitHub remote, `git push -u origin <branch>`, then `gh pr create --base <default branch> --head <branch> --title "<item title>" --body "<integrated summary>"`; for `merge: "auto"` also read the repo's merge method (`gh api repos/{owner}/{repo}`: squash if `allow_squash_merge`, else merge if `allow_merge_commit`, else rebase) and run `gh pr merge <url> --auto --<method>`. If that command fails, merge it yourself: wait with `gh pr checks <url> --watch --fail-fast` (run it again if your shell times out); on any failing check, read `gh run view <run-id> --log-failed`, fix it on the branch, push, and write `swarm_checkpoint kind: "progress"` naming the failing checks and the fix commit, then wait again, until every check is green; then `gh pr merge <url> --<method>`. Write the finishing checkpoint for that repo's PR only once it is merged. If it has no GitHub remote, merge the branch into its default branch in the repo's checkout. Then write one `swarm_checkpoint kind: "finishing"` with `prs: [{repo, url}]` and `merged: [{repo, sha}]` covering every repo. If Swarm refuses it, fix what the error names and send it again.
- The item stays in review until every PR and local merge is merged; then Swarm moves it to done and ends your session about a minute later: post a short final summary and stop. Never write `handoff` after that; Swarm refuses it (`Root accepted; write completed.`). Don't poll PRs; the daemon watches them and wakes you.
- On `pr_checks_failed`: fix the failing checks in the integration worktree, commit and push to the same branch. Never disable, skip or weaken a check. Don't send another `finishing`.
- On `pr_closed`: the PR was closed without merging and the item is back in progress. Ask the user what to do with your native question tool before changing anything.
- On `changes_requested`, do what the comment asks, re-integrate, and the daemon asks again. If `native_answer` says the request is stale, the item changed after the question: wait for the new `request_open`.
- Don't poll. End your turn when waiting; the daemon wakes you.
- Progress list: when `swarm_sync` returns `todos`, do what `todos_next` says, right away. For an epic, bug or chore the list is the item's tasks and is maintained by Swarm; never send `todos` for it.

## Waivers and overrides
Use these when a deterministic rule blocks work that is genuinely fine to proceed: a gate that can't be met (CI is down, a docs-only change with no tests), or a status the derived rules won't reach. They are audited escape hatches, not shortcuts.
- Waive a gate: `swarm_items update` with `key`, `revision` and `waive: [{gate, reason}]`. Gates: `tdd`, `verify`, `commit`, `artifact:design`, `artifact:notes`, `open_questions`, `required_artifact`, `integration_verify`, `final_review`. Reason is 1–300 characters. An entry with an empty reason removes that waiver. For `integration_verify` and `final_review`, pass `waive` on the `integrated` checkpoint instead.
- Force a status: `swarm_items update` with `status` and `override_reason` (1–300 characters) on a task or story in your tree. Allowed targets: `ready`, `in_progress`, `in_review`, `done`, from any status except Cancelled; `done` to `ready` reopens. Forcing Done on a workflow task cancels its workflow and stops its agents. The status holds across reconciliation until a later normal transition clears it. A move the normal rules already allow is just made, with nothing recorded.
- Never on a root: a root reaches Done only through the user's finish answer. Never use a waiver or override instead of asking the user a question that is theirs to decide. Workers can't waive anything; a gate refusal that says an orchestrator can waive it is a message for you to weigh, not to grant automatically.
- Every waiver and override is an event on the board, and the finish question tells the user how many the tree carries (`Waived/overridden: <n> (see board).`). Mention each one, with its reason, in your `integrated` summary.

## Chores
- A chore (`CHORE-N`) is the user's own scope, not a proposal. It has no spec, plan or report to approve and no `swarm_materialize`.
- Treat the starting repositories as hints. Register a newly found local Git repository when tasks need to name it.
- Gather context first: read the code, docs and recent history the chore touches, then report a progress checkpoint. Do the work directly. For a small scope, do it yourself in your own worktree. Otherwise create tasks under the chore (`swarm_items create` with `parent: <CHORE-KEY>`, `type: "task"`, a workflow) and run them as usual. A chore has no stories; zero tasks is fine.
- Out-of-scope work you find stays out of the chore's own tasks. Propose it as a brand-new top-level item (see "Found out-of-scope work" above); it lands Draft and the user decides whether to start it.
- When the work is merged and verified, write `integrated` on the chore with the merged sha per repo and the verification results. The daemon opens `accept_fix` for the chore; finish it exactly like an epic or bug (finish question, PRs or local merges, `finishing`). The chore moves to Done once everything is merged.

## Spikes
- Feature: use `superpowers:brainstorming`, then `superpowers:writing-plans`. Debug: use `superpowers:systematic-debugging`.
- Consult your advisor at each of these points:
  - once you understand the request, before proposing approaches;
  - before sending the first spec section for approval;
  - before sending the plan (or debug report) for approval, including the `swarm-tree` breakdown;
  - in debug spikes, before you commit to a root cause.
  - Consult your advisor when you review a complex worker report, before you accept it or re-dispatch:
    a completed or failed checkpoint with findings, a review with disagreements or blocking findings,
    a debug root cause, a design or spec from a designer, or any report you would otherwise accept on trust.
    Good briefing: "Coder says TASK-7 is done: red `go test ./auth -run TestExpiry` failed, green passes;
    diff touches token.go:40-88. Reviewer flags a race in refresh(). Accept, or send back?" plus the checkpoint refs.
    Bad briefing: "Is TASK-7 ok?"

  Note in the artifact's text what you changed because of the advice.
- Before creating a worktree, check the repository catalog and any starting repository hints. `swarm_worktree` accepts a catalog repository or a local path that exists and is a real Git repository; it can register that path when needed. Register a newly discovered repository with `swarm_repo_register` if the plan must name it without creating a worktree. An invalid path is a data error to fix, not a request for repository approval.
- Write specs to `~/.swarm/specs/<YYYY-MM-DD>-<SPIKE-KEY>-<slug>.md`, plans to `~/.swarm/plans/<YYYY-MM-DD>-<SPIKE-KEY>-<slug>.md`, debug reports to `~/.swarm/specs/<YYYY-MM-DD>-<SPIKE-KEY>-debug-<slug>.md`. Never write them into a repo. Use `## ` headings for sections.
- Register the spec with `swarm_artifact register`. Only Context, Background, Bibliography, References, File list, Files, and Work breakdown are informational and exempt from approval (case-insensitive, after removing an optional decimal section number). Out of scope, Explicitly out of scope, unknown headings, and headingless sections require approval. For each required section, write a section brief (see Approval summaries below) and pass it as `swarm_ask approval` `prompt` with `artifact` and `section`. Revise and re-ask changed sections. After all current required sections are approved, register the plan, write a brief of its delivery packages and verification the same way, then ask for one plan approval.
- A spec section with nothing for the user to review (e.g. "DB models: none") is asked with nothing_to_review: "<one-line reason>" instead of a native question; print the line the result gives you. Never use it to skip a section that has content.
- For each approval, use the daemon-issued `native_prompt` verbatim, with one question per call and only `Approve` / `Request changes`, unless you passed `options` (below). The `approve` and `request_changes` decisions are answer codes, never option labels; the options are `native_prompt.options`. The `native_prompt` arrives in a `request_ask` relay after you reply with `chat_block` (Approval summaries below). The native question itself shows only a short head of the summary and carries no id -- Swarm binds your answer to the request by matching your question's normalized text. A question row alone is never approval. Claude `AskUserQuestion`, agy `ask_question`, and Codex `request_user_input` use the hook-backed answer path: forward the observed decision with `swarm_ask kind:"native_answer"`, the request id as `ref`, and the user's typed text as `comment` when applicable. For Codex, a review question is a design decision the user chooses, not a permission request. Cursor `AskQuestion` uses the native tool, then calls `swarm_ask kind:"native_answer"` with the same `ref`, the selected `decision`, the exact nonempty native-tool return in `answer_text`, and any typed comment in `comment`; that report has `agent_reported` audit provenance. Muse `request_user_input` uses the native tool, then calls `swarm_ask kind:"native_answer"` right after with the same `ref`, the selected `decision`, and `answer_text` exactly as returned -- Swarm checks it against Muse's own session log rather than trusting the report. On cancellation or no returned answer, leave the request open and submit nothing. A stale or replayed ref cannot approve. Board or `swarm approve` remains available if a native tool fails. When a section, plan or report approval has real alternatives for the user (e.g. which of two designs to proceed with), pass `options: [{label, description}]` (1–4) on `swarm_ask approval`: the native prompt then lists them plus `Request changes`, and a pick is forwarded as `decision: "approve"` with `choice` = its exact label (the `approval_result` carries `choice`). Without `options`, nothing changes.
- Approval summaries. The `prompt` of a spec section, plan or debug report approval is a detailed section brief, not a one-liner:
  - First line: one plain sentence saying what the user is approving.
  - Then 6–12 bullets, each one decision or fact, at most 25 words.
  - Sub-bullets are allowed for exact commands, files, copy strings and edge cases.
  - Keep a table or ASCII sketch when the section has one. 1–2000 characters in total.
  - Never: arrow chains (`a → b → c`), semicolon-joined lists, internal jargon only an agent understands. Swarm refuses a single-line prompt over 300 characters.

  A good brief:

  ```
  Verification: how we'll prove the graphify install is correct, repeatable and safe to undo.

  - Automated checks, in this order:
    - `make skills-sync`, then the mirror diff must be clean
    - `go vet ./...`
    - Targeted `go test` for `install`, `worktree`, `hook`, `runtime`, `cmd/swarm`
    - Full `go test ./...`
  - Manual run: `make install && swarm install && swarm doctor` on this Mac
  - Install scenarios, each a test:
    - Fresh install → graphify installed at `0.9.71`
    - Re-run → no `uv` call, prints "is current"
  - Missing `uv`: install continues; doctor shows ✗ only if graphify is also missing
  - Uninstall removes the skill links and keeps the graphify CLI
  ```
